## 1. 产品原则

1. **账号身份先清楚**：每个页面都能通过一致的账户入口确认当前登录主体；账户中心展示服务端确认的邮箱、用户 ID、角色和验证状态。
2. **真实数据优先**：功能骨架可以先落地，真实账务后接；但未接入的数据必须显示“尚未启用/暂无记录”，绝不显示静态假余额、伪造消费或将 `0` 误作真实余额。
3. **用户额度与 Provider 成本分账**：用户购买/获得的额度、对用户计费和退款，与平台向中转站/Provider 支付的成本分开记录。Provider 后台余额不能作为用户余额。
4. **服务端是账务权威**：owner 从会话取得；价格、扣费和退款金额均由服务端计算。浏览器不得提交权威余额、扣费数值、用户 ID 或管理员调整内容。
5. **任务和账务可追溯**：任务状态、用户用量事件、Provider 调用状态和平台成本各有清晰职责，以不可变 ID 关联；重试、超时和迟到结果不能重复扣费。
6. **先可解释再自动化**：首期使用服务端版本化计价和审计管理员调整；支付渠道、自动续费、套餐、税务/发票等需业务与合规确认后再设计。

## 2. 用户侧信息架构

### 2.1 全局账户入口

Studio 顶栏增加统一的用户菜单，头像/首字母只是邮箱派生的展示标记，不存储为独立个人头像。菜单展示已验证邮箱或可读用户标识，并提供：

- 账户中心
- 任务中心
- 设置
- 登出

桌面端用紧凑菜单，窄屏保持触控可达；菜单不以 Provider 状态或余额作为用户身份标识。账户状态加载失败时显示明确的重试状态，不展示过期缓存冒充当前身份。

### 2.2 账户中心页面

路由：`/account` 与 `/zh/account`，分别沿用英文默认路由和中文并行路由。当前阶段提供单页概览与额度/使用记录未启用状态，不宣称完整的分区导航已实现。

- **概览**：已验证邮箱、用户 ID（复制）、账户角色、邮箱验证状态、账户创建时间（服务端具备字段后展示）；最近任务摘要、额度状态摘要。尚未接通的模块用明示状态，不显示伪数据。
- **额度与账单**：可用/冻结额度、当前价格版本、账单流水、充值/管理员调整、退款/释放记录；未接账本时展示“额度服务尚未启用”，不显示 `¥0`、`0 credits` 或模糊的 `---`。
- **使用记录**：任务时间、Studio/任务类型、PaintTrack 逻辑模型、状态、最终用户扣点、失败释放/退款结果；筛选时间、任务类型、状态，分页；点击进入任务详情。只展示用户收费，不暴露 Provider 内部成本。
- **安全与会话**：修改/重置密码、当前会话信息、登出；多会话列表、撤销其他会话、账户导出/删除作为后续阶段，需完整安全与数据保留策略。
- **帮助与政策**：支持入口、点数换算/定价说明、退款与数据保留政策版本及生效时间。

避免重复建“个人资料”页面：当前 users 没有姓名、头像、地区等字段；首期把身份信息集中在账户中心概览，只有当产品确实需要可编辑资料时才增加资料表单和字段。

## 4. 额度和账务领域模型（后续真实数据）

这是待阶段 6.2–6.6 验收的建模方向，不应被前端状态代替：

- **User credit account**：每用户一个账户，标明账本币种/点数单位及创建状态；缓存余额只能作为可重建投影，不是唯一凭证。
- **Immutable ledger events**：至少区分 grant/top-up、reserve、settle、release、refund、admin_adjustment、expiry（若有过期）；事件包含正负方向、单位、来源类型/ID、幂等键、计价版本、创建时间和审计操作者。已入账事件不原位编辑或删除，纠错用反向/调整事件。
- **Reservations**：任务执行前按服务端版本价格冻结预计额度；可用额度与冻结额度分开计算。并发提交在数据库事务/锁内检查并冻结，防止超扣。
- **Settlement / failure handling**：任务成功按创建时固定的报价结算。可确定 Provider 尚未 dispatch 的系统失败，全额释放冻结额度（账本记录对应 `release`/退款效果，不直接改余额）。Provider 已 dispatch 后不得因系统本地错误或结果抓取/持久化失败自动退款；应按真实上游状态处理：上游明确成功则按固定报价结算，上游明确失败则释放冻结额度，上游状态未知则保持 `pending/reserved` 并进入对账，不盲目释放或再次收费。重试沿用 task/attempt 幂等语义，避免重复冻结、结算或释放。
- **Pricing versions**：每个 PaintTrack 逻辑模型的价格由后台管理员动态配置，不在代码、客户端或 Provider 适配器中写死。基础计价结构可采用“参数分档 + 输出数量”（例如按分辨率档位配置单价，再按输出数量计算），但分档边界、各档价格、数量系数及是否启用均属于管理员配置。配置以不可覆盖的新版本发布并设置生效区间；创建任务时保存不可变报价/计价快照，以便价格调整不改变历史任务账单。客户端不能传价格。
- **注册赠送策略**：管理员配置全局开关与赠送额度；系统默认关闭。开启后在注册成功时按当时生效的配置发放一次。配置变更只影响此后新注册的账户，不追溯调整既有用户。发放事件写入不可变账本，并以用户/注册来源唯一幂等键保证重复请求不重复赠送。
- **注册反滥用**：赠送是注册成功时的产品权益，但注册入口必须设置反自动化与滥用防护，重点降低脚本批量注册和一次性邮箱薅赠送的风险。注册风控在账号/赠送入账前执行；拒绝注册或判定为高风险时不得发放赠送。具体手段、阈值与误伤申诉流程须在上线前由产品/安全评估确认，不在本契约中臆定某一家 CAPTCHA、邮箱名单或固定阈值。
- **Provider cost ledger**：独立记录 Provider/上游模型、币种、费用来源和估算/实结状态；与用户账单通过 task/attempt 关联，但不能直接暴露为用户余额。
- **Manual adjustments**：首期如需人工充值，仅管理员服务端接口；强授权、原因必填、幂等请求、审计前后余额和操作者；不得直接 UPDATE 余额绕过账本。
- **Reconciliation**：能够从不可变事件重算可用/冻结余额；检测任务终态与 reservation/settlement 不一致、负余额、重复结算和 Provider 成本缺失，并提供受限修复流程。

### 4.1 已确认的产品规则（2026-11-13）

以下为用户明确确认的产品事实，后续实现不得反向改写：

1. **按模型动态定价**；每个模型的价格、参数分档和版本生效由后台管理员配置，代码不固化具体金额。图片基础计价模板确定为“分辨率分档 + 输出数量”，视频基础计价模板确定为“视频时长 + 帧率”；两类模板的档位边界、单价、数量/时长/帧率系数和启停状态均可由管理员动态调整。创建任务时必须固定当时的报价、规则版本和必要参数快照，后续调价只影响新任务。
2. **积分单位**：最小单位为 **0.1 credit**。账本与余额投影以整数十分之一 credit（`credit_tenths`）存储和运算，展示层可格式化为一位小数；禁止使用二进制浮点数作为权威余额或账务计算表示。
3. **人民币充值方向**：允许用户以人民币充值兑换积分；兑换比例**暂定、尚未确定具体数值**。积分只能用于产品内服务，**不可兑换或提现为人民币**。充值需未来定义人民币金额精度、积分换算/舍入、订单幂等、支付回调和退款合规；未完成前不得开放充值或展示可操作入口。
4. **注册成功时发放赠送**；管理员可配置是否开启及赠送额度，系统默认**关闭**。配置仅影响新注册用户，不追溯修改已有账户。赠送需经过反脚本/批量注册和一次性邮箱滥用防护，并通过幂等账本事件最多发放一次。
5. **确定尚未调用 Provider 的系统失败：全额释放冻结额度。**
6. **Provider 已调用：不因应用侧失败自动退款。** 若上游明确成功，结算固定报价；若上游明确失败，释放冻结额度；若上游状态未知，**持续保持冻结**，直到获得可验证的上游明确结果，或由具备权限的管理员通过受审计的对账/修复流程处理；不得因等待时间过长自动释放，也不能把“未知”推定成失败或成功。

这里“上游失败释放额度”是冻结阶段的释放，不是已结算收费后的退款；若将来支持已结算后的人工冲正，必须另走有审计的反向账本事件。

### 4.2 阶段 6.2 技术契约（设计基线，尚未实施）

本节把 §4.1 产品规则转换为实现约束。这里只批准技术设计方向，不代表已批准数据库迁移、运行代码、管理员 API 或真实收费调用。

#### A. 账本和余额模型

- 每用户一个 `credit_account`，使用明确的整数最小单位；`available` 与 `reserved` 分开。余额字段是事务内维护的可重建投影，不是唯一凭证；权威依据是 append-only ledger events。
- 账本事件不原位 UPDATE/DELETE。事件必须有 `user_id`、事件种类、正整数数量、单位/精度版本、来源类型与 ID、唯一 `idempotency_key`、发生时间及 actor（系统/管理员）。纠错使用反向事件，不改历史。
- 事件模型须显式表示账户资金桶之间的移动，避免把 reserve/release 错记成用户额度净增减：grant 增加 available；reserve 将 available 转入 reserved；settle 消耗 reserved；release 将 reserved 转回 available；已结算后的人工退款/冲正是单独、受审计的反向事件。每次迁移前后都必须满足 `available >= 0`、`reserved >= 0`，且账户投影等于事件流重算值。
- 积分最小单位固定为 0.1 credit；账本数量与余额投影使用整数十分之一 credit（`credit_tenths`），对外展示时再格式化为一位小数。禁止二进制浮点余额和浮点账务运算。由于人民币→积分兑换比例仍暂定，充值金额与积分换算实现不得先行固化；将来报价快照仍需记录单位版本与舍入规则版本。
- 一个任务的初始冻结最多一次（按 task 唯一）；重复提交命中同 owner/idempotency key 时返回原 task 与原 reservation。每个账本动作使用可从稳定业务主键推导的唯一幂等键；并发检查余额必须锁定 account 行或执行等价的原子条件更新。

#### B. 版本化定价和报价快照

- 管理员维护每个逻辑模型的价格规则版本；版本不可覆盖，更新新建版本并设置生效时点。图片规则模板为“分辨率分档 + 输出数量”，视频规则模板为“视频时长 + 帧率”；具体价格、分档边界、时长/帧率参数、数量系数和启停状态全部来自后台配置，不得写死在应用代码中。审核/启用中的价格规则必须有明确状态、actor、变更摘要和审计记录。价格配置与 Provider 成本数据分表，不能把上游结算价直接当用户价。
- 价格规则由服务端匹配逻辑模型和获准的规范化任务参数。图片任务使用“分辨率分档 + 输出数量”模板，视频任务使用“视频时长 + 帧率”模板；每个模型实际采用的档位、价格、系数、参数上限和启停状态由管理员版本化配置。不支持或缺失的参数必须 fail closed，不能默默按默认低价生成。
- 创建任务时，在同一事务/同一可靠幂等协调中解析模型路由、匹配当前生效价格、校验参数并保存不可变 quote snapshot：模型 ID、pricing version、规则摘要/哈希、规范化计价参数、数量原子单位、单位/精度版本、报价时间和过期/失效策略。客户端只能提交模型 ID 与业务参数，不能提交价格、版本、quote 或余额。
- 对已创建任务，调价不追溯；队列等待期间原则上沿用任务创建时的 quote。若 quote 超过明确有效期或管理员紧急停价，任务不得悄悄套用新价，应进入可审计的 `price_quote_invalidated`/人工重报路径；有效期与紧急策略**已于 2026-11-16 由 §4.3.4 收口**（原文「仍待产品定值」仅作追溯，商业参数取值见该节 §J）。
- “价格浮动”由管理员发布新价格版本表达，不意味着调用时按未知上游实际账单自动改变用户报价。若未来要按实耗浮动结算，必须另行定义上限、超额承担者和用户事前同意机制。

#### C. 任务冻结、调用与结算状态

推荐以一个 task-level reservation 覆盖任务的用户报价，不按每个自动重试重复冻结/收费；`provider_calls` 仍只记录上游调用。对同一任务的重试不得重复 reserve 或扩大冻结额。若未来业务决定按 attempt 计价，必须另立产品决策，不由实现默认推导。

| 任务/上游事实 | 账务动作 | 恢复语义 |
|---|---|---|
| task 与 quote 创建成功 | 同一数据库事务创建 task、quote、reserve 及 available→reserved 事件 | 任一步失败全部回滚；幂等重放返回原 task/reservation |
| Worker 在任何 dispatch intent 前确定失败，且任务最终进入系统失败终态 | 全额 release | 暂时性错误若任务还会重试，不释放；等达到终态或确认不再执行后才释放 |
| Provider 明确接受/仍在运行 | 保持 reserved | 轮询与恢复不新增 reserve |
| Provider 明确成功 | settle 固定 quote | task 成功与 settle 必须同事务，或使用唯一 settlement key 的可恢复事务 |
| Provider 明确失败（包括上游明确返回的终态失败） | 全额 release | 依据可验证的上游终态，不因本地 HTTP 断连、解析失败或超时臆测失败 |
| dispatch 后结果未知、进程崩溃或上游无法确认 | 保持 reserved，标记 reconciliation required | 不退款、不重建另一条收费任务；同 Provider/同幂等键恢复或管理员对账 |
| 用户取消且尚未 dispatch intent | cancel + release | 与任务领取/dispatch intent 竞争时必须事务串行化 |
| 用户取消但 Provider 已接受或已成功 | 不因取消动作退款；等上游终态，成功 settle，明确失败 release | 取消任务状态不能覆盖 Provider 成本事实；产品 UI 应区分取消请求与上游终态 |

#### D. 持久化 dispatch 证据及其保证边界

- 当前 `provider_calls.status='submitting'` 在 Adapter 调用前创建，不能证明已 dispatch。现有 `providerInvocationGate` 的 `dispatchedToAdapter` 只是进程内布尔值，进程退出后不可恢复。
- Adapter invocation 之前新增一个持久化 dispatch-intent 写入点，并且该写入必须成功后才允许调用 Adapter；明确 gate rejection/abort 若发生在 intent 之前，可安全认定“未调用”。字段/事件应关联 `provider_call_id`、task/attempt、时间及 gate/adapter 版本，禁止含 prompt、secret 或请求体。
- **不可实现的保证必须讲清**：数据库提交 dispatch intent 与外部 HTTP dispatch 不能组成原子事务。进程可能在 intent 提交后、真正发包前崩溃。因此 intent 的含义是“从此可能已调用”，不是“已确定发包”；该窗口按未知处理、保留 reservation 并对账。这会有保守冻结而非误退款的代价。
- 若 Adapter 返回上游明确的拒绝/终态失败，应持久化可验证的 provider outcome，再释放 reservation；若 gate 证明未进入 Adapter，可按未调用失败释放。任何 intent 之后的无响应/超时/进程中止都不能仅凭本地错误码作退款依据。

#### E. 注册赠送与反滥用边界

> **历史条款适用范围（2026-11-16 一致性复核）：**下列“建号与 grant 同事务”、按策略版本约束唯一性及“验证关系未定”已被 §4.3.5/§4.3.6 取代，原文保留不作实施依据。当前为建号固定资格与策略版本，首次邮箱验证成功且风险允许后发放；唯一性为 `(userId, signup_grant)`，策略变化不能重复领取。验证不因赠送风控失败回滚。邮箱准入以 §4.3.7 G.1、§4.3.8 E.1 为准；审核由本人承担，组织流程按 §4.3.10 简化，不豁免最小权限与隐私门禁。

- 读取赠送配置的当前版本与注册审查结果，成功创建用户时在同一事务内完成账号创建与 grant（若赠送开启且风险门禁允许）；唯一键以新用户 ID/赠送策略版本约束，每个用户只能有一条 signup grant。关闭赠送则不写 grant；配置变更只影响之后创建的用户。
- 反滥用判定须在 grant 前 fail closed：风险服务不可用时不得先发赠送再异步撤销。注册/赠送 API 不接受客户端自报的风险结果、赠送额度或策略版本。
- 反滥用数据最小化：原始 IP、邮箱、设备指纹等不得写入普通账本事件；确有必要的信号应独立限定访问、用途、保存期限和脱敏/哈希策略。一次性邮箱检测不得仅依赖可轻易轮换的单一名单；具体信号组合、供应商、阈值、误伤申诉、隐私告知和保留期需单独安全/隐私评审。
- 注册成功的精确定义、邮箱验证与赠送的关系目前未确定：用户选定注册成功时发放，不等于可擅自假定“提交表单即成功”或“验证邮箱后才成功”。技术实现前要对齐现有 registration 事务和风险门禁，并明确返回给高风险申请的外部响应，避免成为邮箱枚举 oracle。

#### F. 管理员定价/赠送配置审计

- 管理写入口不早于阶段 8 相应管理员强化认证授权；普通 admin MFA 与高影响设置是否要求 step-up，由授权设计评审后定。Provider 写 API 当前关闭，不代表账务管理写 API 已可复用或获批。
- 每次价格/赠送策略变更必须是原子、幂等且审计：操作者、MFA/step-up 上下文、变更理由、前后版本 ID、规范化变更摘要/hash、生效时间、请求幂等键、结果。不得把秘密或用户风控原始信号写入审计。
- 新版本不能改写历史任务 quote 或既有 signup grant；关闭赠送只阻止之后的注册赠送，不追回已发额度；改价不重算已有 reservation。
- 价格与赠送两类配置应分开授权/资源类型，不能把注册滥用信号塞进现有 Provider 配置审计表或放宽现有 Provider 权限边界。

#### G. 数据库事务、角色和恢复

- 任务创建 + quote + reserve + ledger event + account projection 必须由一个受限服务边界协调。优先在同一 PostgreSQL 事务内完成；若现有 Web role 列级权限不允许，则新增窄权限的 billing service/数据库函数，不能为方便而给 Web/Worker 表级写权限。
- Worker 只报告经过验证的 dispatch/provider outcome；结算服务通过 lease/fencing token 与状态条件更新确保过期 Worker 不能重复 settle/release。管理员修复也只能追加调整事件，不能直接改余额。
- 为注册 grant、reserve、settle、release、退款/冲正定义唯一键和状态条件；任务终态与 reservation 不一致由 reconciliation job 扫描并幂等收敛。重放时必须安全，不允许重复赠送、重复扣费或负余额。
- ledger/account 数据库权限需拆分读写列/动作，并建立未授权访问反例；不能依赖应用层约定防止账本 UPDATE/DELETE。

#### H. 阶段 6.2 验收门禁

6.2 设计评审通过前不实施 0024 迁移、不开放收费。技术契约评审至少验证：

1. 最小单位固定为 0.1 credit，账本以整数十分之一 credit 存储；报价精度与舍入已按 §4.3.1 确认，价格生效/失效与报价有效期已按 §4.3.4 收口（商业参数取值待用户拍板），仍需明确管理员配置默认值。人民币兑换比例尚暂定，支付/换算不在首期实现范围。
2. quote 覆盖所有影响计价的规范化输入，历史 quote 对管理员后续改价保持不变。
3. 并发注册只发一笔 signup grant；关赠送或高风险拒绝不发；变更策略只影响新注册；无需假定某一风控供应商。
4. 并发提交/余额不足/同键重放/不同请求复用幂等键/事务中断均无超扣、重复 reserve 或孤儿 task。
5. 每条任务/Provider 状态路径有唯一且可恢复的结算动作；明确失败 release，dispatch 后 unknown 不 release；dispatch intent 写后崩溃按未知保守冻结。
6. 取消与领取/dispatch 竞态、自动重试、多 attempt、迟到成功、上游失败和 worker 崩溃都通过确定性状态表及真实 PG 隔离验收。
7. DB 角色最小权限、ledger 不可变性、余额投影重算、审计完整性与负权限用例通过；不泄漏风控信号、Provider secret 或内部成本。
8. 测试覆盖真实事务/并发/崩溃恢复；仅 fake pool/source-regex 不能作为数据库不变量已通过的证据。
9. 积分账户使用整数十分之一 credit 原子单位，CHECK/写服务拒绝无法精确表示为 0.1 credit 倍数的金额；允许展示一位小数，但禁止浮点账务计算。人民币充值方向只能产生积分充值事件，任何积分兑人民币/提现路径均不存在；充值比例未确认前支付与换算功能保持关闭。

#### 4.3.1 已确认的报价精度与舍入规则（2026-11-13）

以下规则已由用户确认，属于阶段 6.2 技术契约；其中人民币充值的兑换比例和充值换算规则仍另行待定：

1. **最小货币原子单位**：1 个账务原子单位 = 0.1 credit。数据库和权威计算使用整数 `credit_tenths`，展示时格式化为最多一位小数；不得将 JS `Number` 浮点余额或 `0.1` 直接用于账务累加。
2. **固定价配置**：管理员固定价以 0.1 credit 的整数倍配置，服务端将其转换为整数原子单位保存；不把人民币金额、Provider 成本或浮点数作为运行时用户报价的中间权威值。
3. **参数化价格使用定点运算**：分辨率、时长、帧数、输出数量等计价参数先经过服务端规范化，规则使用整数原子单位和有界比例计算；禁止 JavaScript 浮点数直接参与权威报价。计算中间结果保留规则版本定义的定点精度。
4. **最终正向费用向上取整至 0.1 credit 的倍数**：若参数化计算结果不能精确表示为整数原子单位，向上取整到下一个原子单位；非零计价结果最低为 0.1 credit。该方式避免生成无法入账的金额并降低舍入少收；最终报价在任务创建时固定，结算不重算。
5. **不允许隐式截断或语言默认舍入**：`floor`、语言默认 `round`、二进制浮点比较和“按显示值扣费”不能作为账务规则。若最终选择其他舍入方式，必须版本化记录，并保存到报价快照。
6. **边界与失败策略**：缺失、越界、无法规范化或超出规则支持范围的计价参数必须 fail closed，不能因计算异常回退到最低价。超过数据库/实现安全上限的结果应拒绝创建任务，而不是溢出或截断。
7. **报价快照至少保存**：规范化计价参数、价格规则版本、原子单位/定点精度版本、舍入模式版本、计算前的定点结果（或可重算摘要）、最终整数 `credit_tenths`、报价时间和报价有效期。快照不可变，后续改价不影响历史任务。

#### 4.3.2 基础动态计价模板

以下只定义模板结构，不定义任何模型的具体价格；具体配置由后台管理员按模型发布版本：

- **图片模板：分辨率分档 + 输出数量**
  - 服务端先把宽度、高度和输出数量规范化，并依据管理员配置的分辨率档位选择价格项。
  - 价格项至少需要能表达档位单价、输出数量规则、数量上限和启用状态；是否按单张累加、首张基础价加增量价，均由该模型的价格版本明确记录，不能由代码隐式推断。
  - 缺失宽高、无法匹配分辨率档位、输出数量不是正整数或超过管理员上限时，拒绝报价和任务创建。

- **视频模板：视频时长 + 帧率**
  - 服务端先把视频时长和帧率规范化为规则版本要求的定点参数，再匹配管理员配置的时长区间和帧率档位/系数。
  - 价格项至少需要能表达时长计价方式、帧率计价方式、允许的时长/帧率范围和启用状态；按时长分段、按时长原子单位计价或按帧率系数计算，必须由该模型的价格版本明确记录。
  - 缺失或无法规范化时长、帧率不在允许范围、时长/帧率超出管理员上限时，拒绝报价和任务创建。

- **共同约束**：模板只接受服务端规范化后的参数；管理员可以为不同逻辑模型选择不同价格版本和参数值，但不能覆盖历史版本。报价最终转换为整数 `credit_tenths`，按 §4.3.1 的定点计算和向上取整规则处理；客户端只能提交业务参数，不能提交档位、价格、系数或计价版本。

**当前状态：**上述报价精度与舍入规则已确认，但本确认只完成技术契约设计，不授权账本实现、数据库迁移、充值换算或收费功能开放。

#### 4.3.3 计价模板落地细则（2026-11-16 草案，待评审）

本节把 §4.3.2 的“模板结构”推进到可评审、可实现的字段与匹配算法层面。**仍然不含任何具体金额、不含价格生效时点与报价有效期（属独立下一步）、不含 DDL、迁移与运行代码。** §4.3.2 原文保留，作为本节的上级约束，二者冲突时以本节更具体的规定为准；本节与 §4.3.1 冲突时以 §4.3.1 为准。

##### A. 事实基线：计价输入目前只存在一半

落地前必须先承认现状，否则“模板”只是纸面文字：

| 模板所需输入 | 当前真实存在的问题 |
|---|---|
| 图片分辨率档位 | **存在**。`payload.aspectRatio` 收敛为 6 个枚举，`payload.size` 由 `sizeForAspectRatio` 一一映射为固定字面量（`1024x1024`、`1536x864`、`864x1536`、`1365x1024`、`1024x1365`），服务端强制两者一致（`lib/server/tasks/taskSubmission.js`） |
| 图片输出数量 | **不存在**。`createImageTask` 只提交 `logicalModelId/prompt/aspectRatio/size`，payload 白名单与校验都没有数量字段 |
| 视频时长 | **不存在**。`video.generate` 没有任何字段级校验，Studio 也没有视频提交客户端 |
| 视频帧率 | **不存在**。同上 |

由此得出一条硬结论：**账本启用前必须先扩展计价参数契约，这本身是独立授权步骤。**在参数缺失的情况下，禁止用“数量=1 / 时长=5 秒 / 帧率=24”之类默认值补齐。这里要区分两件不同的事：

- **产品事实**：若产品明确规定“当前 `image.generate` 每个任务只产出一张图”，则 `outputCount=1` 是事实，可以写入报价快照，并须在快照中留下“该值来自服务端任务类型定义”而非客户端自报的来源标记。
- **计费兜底**：若数量参数尚未定义就按 1 计、或时长缺失就按最短档计，那正是 §4.3.1 第 6 条禁止的“回退最低价”，必须 fail closed。

##### B. 规范化后的报价输入（服务端权威）

报价只接受服务端规范化产物，客户端提交的任何档位、单价、系数、版本、数量上限一律拒绝（与现有 `FORBIDDEN_KEYS` 机制同向扩展）。

- **图片**：`{ resolutionKey, outputCount }`
  - `resolutionKey` 取 `size` 字面量本身（如 `1024x1024`），不做归一化、不做比例重算。
  - `outputCount` 为正整数；当前由任务类型定义给出，将来若放开 `n` 参数，须先扩 `validatePayload` 白名单并做整数与上限校验，不得让客户端直接决定计费数量。
- **视频**：`{ durationMs, fps }`
  - `durationMs` 为**毫秒正整数**，是唯一权威时长单位；展示层再做秒/毫秒换算，避免以浮点秒作为账务输入。
  - `fps` 为正整数，且必须是价格版本显式登记的档位。
  - 两者当前均不存在，故视频报价在参数契约补齐前**必然不可用**，这是设计结论而非缺陷。

##### C. 图片档位匹配

- 采用**字面量精确匹配**：以 `size` 精确命中价格版本中的档位键。不做区间吸附、不做比例容差、不取“最近档位”。
- 理由：服务端已把宽高收敛为有限闭合集合，精确匹配没有边界歧义、可审计、可用一条断言覆盖；区间匹配则会引入“边界宽度算哪档”的长期争议。
- 命中不到档位 → fail closed（`PRICING_RESOLUTION_UNMAPPED`）。将来源码新增 `size` 而未同步发布新价格版本时，新尺寸的任务会被拒绝创建，而不是被算成旧档——这是有意为之的失败方向。
- 档位可被管理员置为不启用；命中禁用档位等同未命中，同样拒绝创建任务。

##### D. 图片数量计价形态（由价格版本显式声明，代码不得推断）

`quantityMode` 三选一，必须写入价格版本：

| `quantityMode` | 含义 | 总价（整数原子单位，`A`） |
|---|---|---|
| `per_unit` | 每张同价 | `unit × n` |
| `base_plus_increment` | 首张基础价 + 后续增量价 | `base + increment × (n − 1)` |
| `tiered_total` | 按数量区间取档总价（区间左闭右开） | 区间对应的档位总价 |

- `n` 必须满足 `1 ≤ n ≤ maxOutputCount`；超出上限 → `PRICING_OUTPUT_COUNT_EXCEEDS_LIMIT`，**不截断、不按上限计费**。
- `n` 非正整数（`0`、负数、小数、字符串数字）→ `PRICING_OUTPUT_COUNT_INVALID`。
- 任何乘法一律在最终原子化前保持定点/整数中间值。

##### E. 视频时长与帧率匹配

- **时长区间左闭右开** `[startMs, endMs)`，保证任一时长唯一命中一段，边界值归属明确。
- 价格版本发布时必须校验时长区间集合：**不重叠、无空洞、覆盖声明范围、`startMs < endMs`、非负**；任一不满足即拒绝发布（`PRICING_CONFIG_INVALID`），不允许“先发出去再运行期补救”。
- **帧率只做枚举匹配**，未登记的帧率 fail closed（`PRICING_FPS_UNMAPPED`）；不做“吸附到最近档位”，否则用户无法从账单反推自己被按哪档收费。
- 帧率对价格的影响以**有理数系数**表达（`numerator`/`denominator` 均为整数，`denominator > 0`），禁止浮点系数参与权威计算。
- `durationMode` 三选一，必须写入价格版本：
  - `per_second`：按秒定点计价，秒的小数部分保留到版本声明的定点精度，最终统一舍入；
  - `band_total`：按命中时长区间取档位总价，时长只在区间内起作用；
  - `per_frame`：总帧数 = 时长 × 帧率（须声明是否整除、余数如何处理），再按帧单价计价。
- 时长超过 `maxDurationMs` 或低于最短支持值 → `PRICING_DURATION_INVALID` / `PRICING_DURATION_UNMAPPED`。

##### F. 原子化、舍入与溢出

- 计算顺序：规范化输入 → 定点/整数中间结果 → **单次**向上取整到 1 个原子单位（0.1 credit）→ 非零最低 1 原子单位。
- **只在最终一步取整**，禁止对每个因子分别取整后相乘：`per_unit` 场景下逐因子取整会系统性高估，和“少收”同样是错误。
- 中间结果一律用整数或 `BigInt` 承载；结果超出 `Number.MAX_SAFE_INTEGER` 或未来数据库列上限时拒绝创建任务（`PRICING_RESULT_OVERFLOW`），不截断、不回绕。
- 报价是纯函数：同一 `(pricingVersion, 规范化输入)` 必须产出逐位相同的 `credit_tenths` 与规则摘要 hash，便于事后对账复算。

##### G. 失败语义与对外错误面

- 统一对外粗粒度错误 `PRICING_UNAVAILABLE`，内部子码用于日志与运维，响应体**不得**回显档位、单价、系数、版本内容或内部成本。
- 子码清单：`NO_ACTIVE_VERSION`、`TEMPLATE_MISMATCH`、`RESOLUTION_UNMAPPED`、`OUTPUT_COUNT_INVALID`、`OUTPUT_COUNT_EXCEEDS_LIMIT`、`DURATION_INVALID`、`DURATION_UNMAPPED`、`FPS_UNMAPPED`、`RESULT_OVERFLOW`、`CONFIG_INVALID`。
- 全部子码一律导致**任务不创建**，不存在“报价失败但照常执行”的分支。这与 §4.3.1 第 6 条一致：不计费就不能开工，而不是先干活后补价。

##### H. 配置数据形状（逻辑草案，不含 DDL）

价格版本级字段：`modelId`、`templateType`（`image_resolution_quantity` / `video_duration_fps`）、`currencyUnit = credit_tenths`、`roundingMode = ceil_to_atom`、`precisionVersion`、`roundingModeVersion`、`quantityMode` 或 `durationMode`、`maxOutputCount` 或 `maxDurationMs`、允许帧率集合、启用状态、版本摘要 hash。
计价项级字段：档位键（`resolutionKey`，或 `durationBandStartMs`/`durationBandEndMs` + `fps`）、`unitPriceTenths`（≥ 0 整数）、`fpsNumerator`/`fpsDenominator`、`enabled`。

- 同一版本内档位键必须唯一；重复键视为配置不自洽，发布即拒绝。
- `unitPriceTenths = 0` 合法（免费档），负值非法；免费档仍须出现在报价快照中，不能靠“没有档位”表达免费。
- 版本不可覆盖，历史任务快照永久指向其创建时的版本。

##### I. 本节的验收要点（供评审与后续实现门禁使用）

1. 任意缺失/越界/无法规范化的参数都返回 fail closed，且**不存在**回退默认值或最低价的代码路径。
2. 同一输入的报价可重复复算，逐位一致；快照含足够信息在无运行时配置的情况下重算。
3. 配置发布期校验：分辨率键唯一、时长区间不重叠无空洞、帧率为整数正数、系数分母非零、上限为正整数。
4. 图片档位与现有 6 个 `size` 完全对齐；源码新增尺寸而价格版本未跟进时，任务被拒绝而非静默降档。
5. 只在最终一步取整；对 `per_unit` 与 `base_plus_increment` 各构造一组会产生累积误差的输入，证明未逐因子取整。
6. 报价失败不产生任务、不产生 reservation、不产生账本事件（待账本实现后由真实 PG 负例覆盖）。

价格生效时点与紧急停价策略、报价有效期与过期后的处理路径（**2026-11-16 已由 §4.3.4 收口，本条仅作追溯**）、赠送额度与有效期、反滥用阈值与申诉、上游长期未知的人工处置 SLA，均属后续独立小步骤；0024 迁移、账本表、结算代码、管理员定价 API 仍未实现也未授权。

#### 4.3.4 价格生效与报价有效期（2026-11-16 草案，待评审）

本节收口 §4.2 B 中「版本生效 / 紧急停价 / 报价有效期仍待产品定值」的空白。**仍然不含具体金额、不含 DDL、迁移与运行代码。** 与技术约束不同，本节 §J 列出的商业参数**不预设取值**，只给推荐与影响，须由用户拍板后才写入实现。

##### A. 术语与不变量

| 术语 | 定义 |
|---|---|
| 价格规则版本（pricing version） | 某逻辑模型某模板下的一组不可变计价项，一经发布不得修改，只能新建版本 |
| 生效时点 `effectiveFrom` | 版本开始对**新任务**生效的 UTC 时刻，秒级精度 |
| 撤销时点 `revokedAt` | 版本被紧急停用的 UTC 时刻；缺省为空表示未撤销 |
| 报价（quote） | 任务创建时固定下来的计价结果快照，含版本 ID、规范化参数、`credit_tenths` 与 `expiresAt` |
| 派发（dispatch） | `dispatch intent` 持久化成功、可能已向上游发包的那一刻（沿用 §4.2 D 的定义） |

不变量（实现中不得违反）：

1. **同一 `modelId` 在任一时刻最多一个可报价版本**；判定由查询保证，不依赖后台状态迁移（见 §B）。
2. **版本不可变性**：`effectiveFrom` 之后不允许再修改任何计价项、上限、系数；要改只能新建版本并给新的 `effectiveFrom`。
3. **历史不可改写**：已创建任务的 quote 永久指向其创建时的版本 ID，任何调价、撤销、停价都不重算历史 quote。
4. **quote 只由服务端产生**：客户端不能提交 `expiresAt`、版本 ID、`credit_tenths` 或任何影响有效期的参数。

##### B. 生效判定：以时间比较为准，不以状态字段为准

**这是本节最重要的技术选择。** 生效与否必须由一次查询直接判定，不允许依赖「后台定时任务把 scheduled 改成 active」：

```
在任务创建事务内，取该 modelId 下满足以下条件的版本，按 effectiveFrom 倒序取第一条：
  publishedAt IS NOT NULL            -- 已发布（草稿不可报价）
  AND effectiveFrom <= now()          -- 已到生效时点
  AND (revokedAt IS NULL OR revokedAt > now())
```

- 被新版本接替的旧版本**不需要**被改写状态：新版本 `effectiveFrom` 更晚，倒序第一条自然命中新版本，旧版本即「事实上的已被取代」。这样避免了「定时任务没跑 → 价格没切」这类静默故障。
- `now()` 必须取**数据库时间**，不得取应用进程时间。多实例部署下进程时钟漂移会让同一请求在不同实例报出不同价格，这类分歧无法事后对账。
- 版本表中仍保留 `status` 字段用于后台展示与审计（`draft`/`published`/`revoked`），但**它只是派生展示，不参与报价判定**；若展示与时间判定不一致，以时间判定为准并报警。
- 若查询无结果 → `PRICING_NO_ACTIVE_VERSION`，任务不创建（fail closed）。

##### C. 生效时点：立即生效与预约生效

- 支持两种发布方式：**立即生效**（`effectiveFrom = now()`）与**预约生效**（`effectiveFrom > now()`）。
- 发布校验（发布即拒绝，不进入运行期）：
  1. 同一 `modelId` 的版本时间轴**不得出现相同 `effectiveFrom`**（同一秒两个版本会造成倒序结果不确定）；
  2. `effectiveFrom` 不得早于当前时间（不允许「补一个过去生效」的版本，否则历史任务与新任务的计价依据会在审计上不可分辨）；
  3. 预约版本允许存在多个（构成未来时间轴），但不允许「插入到已生效版本之前」。
- 预约版本在到点前对报价完全不可见（`effectiveFrom <= now()` 不成立），无需人工启用。
- 允许**取消预约**（未到点的版本置为 `cancelled`，物理保留记录），取消不影响任何已创建任务。

##### D. 紧急停价：必须区分两种语义

历史文档把「紧急停价」与「quote 失效」混在一起写，会直接导致实现时误伤在途任务。本节拆成两个独立操作，权限与影响面不同：

| 操作 | 语义 | 影响新任务 | 影响在途任务 | 风险等级 |
|---|---|---|---|---|
| `revoke`（停售） | 该版本从此不再对外报价 | 立即挡掉（`revokedAt <= now()`） | **不影响**，已创建的 quote 照常执行 | 常规运营 |
| `invalidate-outstanding`（使在途报价失效） | 额外让尚未派发的 quote 作废 | 同上 | 未派发的 quote 进入 `price_quote_invalidated`，冻结额度按 §F 释放 | **高风险**，需二次确认 + 独立审计 + 明确理由 |

- **默认只做 `revoke`。** `invalidate-outstanding` 必须作为独立的高风险开关，不能与停售绑在同一个按钮上——否则一次「改价停售」会连带打死排队中的正常任务，用户侧表现为「莫名失败」。
- 两种操作都只写 `revokedAt` / 失效标记，**不删除、不改写版本与历史 quote**。
- 停售后若该模型无其它可报价版本，新任务一律 `PRICING_NO_ACTIVE_VERSION`；这属于正常的「模型下架」，UI 应显示「模型暂不可用」而非「系统错误」。

##### E. 报价有效期：只约束「派发前」的排队窗口

这是最容易做错的一处，必须写死语义：

- **有效期约束的是「从 quote 创建到 dispatch intent 写入」这段等待窗口**，不是整个任务生命周期。
- **一旦 dispatch intent 写入，quote 即固定为结算依据，不再受有效期影响。** 理由：上游成本已经发生，此时让 quote 过期既不能让成本消失，也不能对用户改价——那只会制造「任务跑完了却不敢结算」的死结。
- 因此 `expiresAt` 的正确用途是：**限制任务在队列里空等多久还可以按老价格执行**。它防的是「价格已调整而长队任务仍按旧价成交」，不是「上游跑太久」。
- 起算点：quote 创建成功时刻（数据库时间），不是客户端请求到达时刻，也不是前端校验时刻。
- 有效期内：任务可排队、可自动重试（同 task 不重复 reserve，沿用 §4.2 C），**不重新报价**。
- 过期判定同样取数据库时间；过期后无论队列是否即将轮到，都不再派发。

##### F. 过期与失效后的资金语义

| 情形 | 是否已 dispatch | 账务动作 | 说明 |
|---|---|---|---|
| quote 过期，任务尚未派发 | 否 | **全额 release**，任务进入 `price_quote_expired` 终态 | 确定未调用，符合 §4.1 第 5 条 |
| 紧急失效在途报价，尚未派发 | 否 | **全额 release**，任务进入 `price_quote_invalidated` | 同上，但由管理员动作触发，须记 actor |
| quote 过期，但已派发 | 是 | **不受影响**，按原 quote 走 settle / release / unknown | 见 §E，成本已发生 |
| 停售（`revoke`）后，在途任务已派发 | 是 | 不受影响，按原 quote 结算 | 停售只挡新任务 |
| 停售（`revoke`）后，在途任务未派发 | 否 | 仍可派发并按原 quote 结算 | 这是 `revoke` 与 `invalidate-outstanding` 的关键区别 |

- **不允许「过期后自动按新价重报并继续执行」**。那等于在用户不知情时改价，直接违反 §4.2 B「不得悄悄套用新价」。若将来要支持重新报价，必须是**用户显式确认**的新请求（新幂等键、新 quote、新 reserve），不能复用原任务。
- 所有释放事件必须带 `release_reason`（`quote_expired` / `quote_invalidated` / `system_failure`）与幂等键，便于对账区分「自然过期」与「人为干预」。

##### G. 事务与竞态边界

- 「读取生效版本 → 计算报价 → 写 quote → 写 reserve → 建任务」必须在**同一个数据库事务**内完成（§4.2 G）。生效版本的读取也在这个事务里，避免「先算价、后取版本」的 TOCTOU。
- `expiresAt` 在事务内由 `quote.createdAt + validityMs` 计算，不取应用进程时间。
- 过期判定与派发之间的竞态：「检查未过期 → 派发」两步之间仍可能跨过 `expiresAt`。处理原则是**以 dispatch intent 写入时刻为准**：如果 intent 写入时已过期，则不派发并走释放；写入后才过期则视为已派发，继续执行。这一窗口无法用锁消除（外部发包不在事务内），按**对用户有利且可解释**的方向处理：已派发就按原价结算，不追溯加价。
- 定时清理任务不得直接 `UPDATE` 任务状态绕过账本；只能追加释放事件并做条件更新（`WHERE status='reserved' AND expires_at <= now()` 之类），保证幂等。

##### H. 审计与可解释性

- 版本发布、取消预约、`revoke`、`invalidate-outstanding` 四类操作全部落审计：操作者、MFA/step-up 上下文、理由（必填）、前后版本 ID 或受影响 quote 数量、请求幂等键、结果。
- 用户侧可见：任务因过期或失效结束时，必须给出**可读原因**（「报价已过期，未产生扣费」/「该模型已暂停，未产生扣费」），不能只抛 `TASK_FAILED`。
- 内部不得把单价、系数、档位、版本内容写进用户可见响应或普通日志（沿用 §4.2 F 与 §4.3.3 G）。

##### I. 对外错误面

- 新增可对外暴露的粗粒度码：`PRICING_QUOTE_EXPIRED`、`PRICING_MODEL_UNAVAILABLE`（无生效版本或已停售）、`PRICING_QUOTE_INVALIDATED`。

**A. 报价版本头：先定时间轴，再判撤销，绝不回退**

- 对同一模型，发布/取消预约/撤销/新任务选价都进入同一个模型级事务串行化边界；先获取锁，再采样一次数据库 `clock_timestamp()` 为 `selectionAt`。不靠应用时钟或事务开始时的 now()。发布与报价并发以锁顺序形成可审计先后，不能只说“同事务”便假定已无竞态。
- 取消预约是持久化、受审计的业务事实 `cancelledAt`，不是仅改变展示 status。取消仅可在获取同一模型锁后的数据库实时时刻严格小于 effectiveFrom 时完成；到点不能再走取消，只能撤销。取消记录与版本均保留，不能事后取消已生效版本使历史时间轴消失。
- 候选集：该模型已发布、`effectiveFrom <= selectionAt`、且从未在生效前合法取消的版本。**此时不排除撤销版本**。在候选集中按 effectiveFrom 取唯一最新头；同生效时刻冲突由数据库唯一性和发布校验拒绝，不以任意 ID 排序掩盖冲突。
- 无头则拒绝报价；头已撤销也拒绝报价，**不继续找旧版本**。只有另行受审计发布的新版本到点才能恢复服务；未来预约版本仍会在各自时点成为新头，因此撤销某一版本不等于永久下架整个模型。永久停模型属于模型启停边界，不由本步擅自新增。
- 草稿/合法取消的预约不成为头；取消未来 V2 时当前 V1 仍有效，因为 V2 从未生效；当前 V2 撤销时即使 V1 未撤销也不可回退。数据库保证发布价格内容不可被就地编辑，生命周期事件与不可变价格内容分开。
- 立即发布取锁后数据库时刻，预约发布用同一时刻验证未来时间和精度约束；不使用客户端时间，也不靠定时任务把 scheduled 改 active。秒级时间轴精度与同秒冲突仍遵守既有契约，不通过悄悄移动用户预约时点解决冲突。

**B. 到期释放与首次 intent：同一串行化边界内二选一**

- 首次派发、到期释放、取消释放以及未来获准的人工失效，统一使用 task/reservation/account 的固定锁顺序，具体 SQL 与角色能力须在迁移前另审；不得为方便扩大 Web/Worker/cleanup 授权。
- 获取锁后先核对持久化的 task 全历史 provider call/attempt intent 证据，而非只看本轮 attempt、进程内标记或当前 call status。已有任意历史 intent 的任务，走 C，不能进入普通 quote 到期释放。
- 从未有 intent 时，锁后采样数据库实时 `decisionAt`；严格 `decisionAt < expiresAt` 才能以同一条件化状态转换写入首个 intent，等号视为已过期。quote 必须仍有效、reservation 未释放、lease/fencing 有效。该采样与转换不得夹入事务外 IO/网络等待，后续 SQL 必须复核条件；不拿事务开始时间补签为“未过期”。
- 在该串行化决定点已到期则在同事务追加唯一 release 事件、更新投影并结束未派发任务；失败全部回滚。后台扫描只负责发现候选，不能用 WHERE expires_at <= now() 直接释放。
- intent 提交成功才允许调用 Adapter；过期释放先获锁，则后续派发失败且零 Adapter 调用；intent 先成功，则过期扫描不可释放。没有持久化意图的回滚事务不能调用 Adapter。
- **保证边界：**采用锁内数据库决定点，而不是宣称能把到期瞬间、事务提交和外部 HTTP 原子绑定。决定点后可能跨过 expiresAt 才提交/发包；此时保留已确定的原 quote。intent 表示“可能调用”，不证明发包或成本发生；提交后发包前崩溃仍按 unknown 保守冻结，不能自动退款。

**C. 历史 intent 的恢复：到期不能覆盖上游事实**

- 任意历史 intent 后出现超时/失联/崩溃，即使当前 attempt 尚未发包或 quote 已过期，也不能认定该任务从未调用。保留原 quote、reservation、Provider 与调用幂等身份，沿现有恢复协议取可验证结果，不新建收费任务、不换 Provider 重提。
- 明确成功 settle，明确失败按既有契约 release，未知继续冻结并对账。不得以到期或用户取消代替上游结果；不在本步添加“清空历史 intent 以重试”的旁路。确定未 dispatch 的证明与人工修复仍须独立受审计，不给普通到期扫描此能力。

**A. 已核验的现状与缺口**

- registration.js 的 register/verify-email 各使用全局 auth_rate_limits bucket，每分钟最多60次；不是每IP/设备/账号的防赠送滥用规则。verifyEmail 消费 token 与写 email_verified_at 同事务，尚无赠送资格、风险决策或申诉记录。
- registrationHttp.js 校验同源、JSON与2048字节请求体、输入字段，注册无邮件通道早拒绝；只向服务传 requestId，没有可信客户端IP、设备或风控结果上下文。HTTP 202 accepted 对合法重复邮箱保持一致，不能据此发额度或公开账号存在性。
- authPolicy.js 的 Origin/Sec-Fetch-Site 检查是请求来源约束，不是反机器人身份凭证。现有限流、同源检查和邮箱验证都不能单独证明“每个用户只注册一次”。

**B. 拆分注册保护与赠送审查**

注册服务的容量保护继续服从现有认证契约，本步不修改60次/分钟或KDF并发界限。赠送单独使用 allow / review / deny 决策：

| 决策/事实 | 账号与赠送语义 |
|---|---|
| 未验证邮箱 | 固定建号时资格，不发赠送；不因待验证而消耗资格 |
| 已验证、风险允许、存在资格 | 受限事务内写唯一 signup_grant 并消费资格 |
| review或风险依赖故障 | 可完成邮箱验证，赠送保持待审核、不消费资格、不先发后撤 |
| deny（仅赠送） | 不发赠送、保留审计与申诉路径；不因此自动禁登/删除账号 |
| 建号时无赠送资格 | 明示该账号无该项注册赠送资格，不因后来开启而补领 |
| 已发放 | 重放只返回原事实，不二次入账、不重置资格 |

独立安全事件导致账号封禁属于另一授权流程，不混入赠送拒绝。review不能自动超时变allow；永久有效指已入账额度，不代表待审申请永远不需处理，审核SLA见F。

**D. 可信网络来源与隐私（候选）**

- 不直接信任客户端X-Forwarded-For/X-Real-IP；部署边界/可信代理未确认时，不解析这些头伪造风险身份。IP缺失/无法验证不得映射成一个共享占位IP形成全站连坐；改为review，并记录来源不可用原因。当前部署后置，故可信IP接线仍是开启自动grant前的阻断项。
- 仅为频次关联保存规范化来源的服务端带密钥HMAC及key版本；普通hash不足以防低熵IP枚举，HMAC也不是匿名化。密钥由未来可信边界注入，不写根.env、不落浏览器/普通日志；轮换期间保证窗口计数连续，不重置风控。

**E. 资格、风险决策与账本的绑定**

#### 4.3.20 原子任务强制绑定可信路由快照（2026-11-17）

§4.3.19 的遗留缺口是：`routeResolver` 可选，未传时任务仍能以 `logical_model_pk`/`route_snapshot` 全空的形态落库并冻结额度——等于"钱先冻住，执行身份还没锁定"。本步把这条路径封死，只改内部协调器与其测试，**不新增迁移、不改权限、不接HTTP**。

契约变化：

1. `createAtomicTaskPricingStore({ pool, routeResolver })` 在**构造期**要求 `routeResolver.resolve`，缺失即 `TypeError('trusted routeResolver required')`；
2. `submit()` 删除 `route` 入参，调用方无法临时塞入未受信的路由；
3. 解析结果必须通过 `assertTrustedRoute()`：`logicalModelPk` 为小写/大写 UUID、`routeSnapshot` 为普通对象、`routeSnapshotVersion` 为正整数且等于快照内 `snapshotVersion`、`routeSnapshotHash` 为 64 位小写十六进制且等于 `sha256(stableStringify(routeSnapshot))`、快照 `logicalModelId` 与请求一致、`capabilitySnapshot.operation` 与 `taskType` 一致；
4. 事务内锁定模型后再做二次比对：`logicalModelPk === 模型行 id` 且 `routeSnapshot.logicalModelVersion === catalog_version`，防止"价格用A模型、路由指向B模型"或目录版本漂移；
5. 所有路由失败在**事务外**抛出（`MODEL_ROUTE_REQUIRED` / `MODEL_ROUTE_INVALID` / `MODEL_ROUTE_HASH_MISMATCH`），连事务都不开，因此不可能留下 task、quote 或冻结记录。

为什么哈希要自己重算：路由快照是冻结额度的执行依据，数据库只存 jsonb 与哈希，无法校验二者对应关系；JS 侧在写入前重算 `sha256` 是唯一能拦住"改了快照没改哈希"的位置，属于与 `pricing_quotes.snapshot_hash` 同类的自洽校验。

#### 4.3.21 冻结额度的终态裁决 settle/release（2026-11-17）

§4.3.19 只做到"冻结"：任务成功或失败后，冻结额度没有任何合法出口，余额会永久停在 `reserved_tenths`。本步补上唯一出口，并刻意把它压到最小：**全额**结算或**全额**释放，不做部分结算。

为什么不能直接改 `credit_reservations.status`：0024/0026 给 `credit_reservations` 挂了语句级不可变触发器（`credit_reject_mutation()` 与 `atomic_reserve_reject_mutation()`），任何 `UPDATE/DELETE/TRUNCATE` 都直接 `42501`。要让状态可迁移，就得拆掉这两道不许改历史的护栏——代价远大于收益。因此 0027 改为**追加式**：

- `credit_reservations` 继续不可变，冻结事实永不被改写；
- 新增 `credit_settlements(task_id PK, user_id, kind, credit_tenths, event_id, created_at)`，一个任务最多一行终态，`kind IN ('settle','release')`，`event_id` 与 `credit_ledger_events(id,user_id,task_id,credit_tenths)` 组成复合外键，保证裁决行与被引用的账本事件在用户、任务、金额上完全一致；
- 终态表同样挂语句级不可变触发器（`CREDIT_SETTLEMENT_IMMUTABLE`）、`REVOKE ALL ... FROM PUBLIC`，只有专用 owner 有 `SELECT, INSERT`。

账本形状随之收紧而非放宽：`credit_ledger_events.kind IN ('reserve','settle','release')`，且 `idempotency_key = kind || ':' || task_id::text`（一条约束同时锁住 kind 与幂等键前缀）；原 `(task_id)` 唯一索引换成 `(task_id, kind)`，含义变成"每个任务每种事件至多一条"，仍然是每任务最多 3 条事件。未知 kind（如 `refund`）会被 CHECK 拒绝，已验证返回 `23514`。

`credit_finalize_task(p_user_id,p_task_id,p_outcome)` 的裁决顺序（SECURITY DEFINER，owner 所有，仅 owner 有 `EXECUTE`）：

1. 参数校验，`p_outcome` 只接受 `settle`/`release`，否则 `22023 CREDIT_OUTCOME_INVALID`；
2. 取 `pg_advisory_xact_lock(hashtextextended('credit_finalize:'||task_id, 627))` 串行同一任务的裁决——用 advisory lock 而不是 `SELECT ... FOR UPDATE`，因为行锁子句会要求超出最小权限的表级 UPDATE（这正是 0026 踩过的坑）；
3. 已有终态则同 `user_id`+同 `kind` 返回原 `event_id`（重放），否则 `23505 CREDIT_SETTLE_CONFLICT`；
4. 冻结记录不存在 → `55000 CREDIT_RESERVE_NOT_FOUND`；任务不存在 → `55000 CREDIT_TASK_NOT_FOUND`；
5. 终态门禁：`settle` 只允许 `status='succeeded'`，`release` 只允许 `failed`/`cancelled`，其余 `55000 CREDIT_TASK_NOT_TERMINAL`——排队或执行中就扣费/退费一律拒绝；
6. 单语句完成扣减：`UPDATE credit_accounts SET reserved_tenths=reserved_tenths-amount, available_tenths=available_tenths + (release?amount:0) WHERE user_id=$1 AND reserved_tenths>=amount RETURNING *`，不存在行则 `55000 CREDIT_RESERVED_UNDERFLOW`，因此不可能出现负冻结；

#### 4.3.22 终态结算扫描：Worker 终态任务的自动收敛（2026-11-17）

§4.3.21 的裁决是"能结算"，但没人结算：Worker 只写任务状态，`credit_finalize_task` 需要宿主显式调用。若靠人工逐笔触发，一旦漏掉，余额就永久停在 `reserved_tenths`。本步补的是**收敛路径**，并且刻意不扩大任何写权限。

关键取舍：**不给 Worker 账务权限**。Worker 进程一旦能调裁决函数，等于把"执行结果"和"扣费"合并到同一权限域，泄漏面远大于收益。因此收敛放在账本宿主侧，形态是"只读扫描 + 逐笔裁决"：

- 0028 新增只读函数 `credit_pending_settlements(p_limit integer)`，`STABLE SECURITY DEFINER`、owner 所有、仅 owner 有 `EXECUTE`，`REVOKE ALL ... FROM PUBLIC`；
- 候选条件是"有冻结记录 `r` + 任务属于同一用户 `t` + 无终态行 `s` + 任务状态 ∈ (`succeeded`,`failed`,`cancelled`)"，`LEFT JOIN credit_settlements` 天然排除已裁决项，所以重复扫描只会返回剩余行；
- 结局由数据库按任务状态给出：`succeeded` → `settle`，其余两种终态 → `release`，**JS 不自行推断**；
- 批次区间 1..500，越界 `22023 CREDIT_SWEEP_LIMIT_INVALID`；JS 侧用同一上限做前置校验，避免两端漂移；
- 冻结表只补列级 `SELECT(task_id,user_id,credit_tenths,reserve_event_id)`：这些行本就由 owner 写入，读回不增加新信息，`UPDATE/DELETE/TRUNCATE` 仍由不可变触发器直接 `42501`。

JS 侧在 `creditSettlement.js` 增补两个方法：`pending({limit})` 只读列出候选（返回 `{taskId,ownerId,creditTenths,outcome}`）；`sweep({limit})` 先取候选再逐笔 `finalize`。**每笔裁决是独立事务**，因此一笔失败不会回滚已提交的另一笔；已登记的 `SettlementError`（如 `RESERVED_UNDERFLOW`）记录到 `failed` 后继续处理剩余候选，未知错误（连接中断、权限变更）必须上抛并中止本轮，不能被当成"已收敛"。重复调用 `sweep` 在收敛完成后返回 `examined=0`，不会重复扣减或重复退回。

本步**不新建表、不改 schema**：0028 的 snapshot 与 0027 内容完全一致（仅新 id/prevId），迁移门禁按 tag 声明安全扩展条数（0028 为 4 条：owner 守卫、创建函数、撤权、授权与移交所有权）。

#### 4.3.24 额度发放入口：开户、grant 事件与运维 CLI（2026-11-17）

#### 为什么必须先做发放

0024–0028 把冻结、结算、释放都做完了，但账本只有"扣减"方向：`credit_initialize_zero_account()` 在仓库里零调用方，注册流程不建账户；`credit_ledger_events.task_id` 为 `NOT NULL`，`shape_check` 只允许 `reserve/settle/release` 且强制 `source_type='task'`、`actor='system'`、幂等键 `kind||':'||task_id`。也就是说**任何用户都不可能拥有余额**，一旦把 HTTP 提交接上原子链，所有请求都会以 `CREDIT_INSUFFICIENT` 或 `CREDIT_ACCOUNT_NOT_FOUND` 被拒。因此发放必须排在 HTTP 收费之前。

#### 账本形状：两个事件族

`task_id` 改为可空，`shape_check` 拆成互斥的两支：

| 事件族 | 条件 |
|---|---|
| 任务族 `reserve`/`settle`/`release` | `task_id IS NOT NULL`，`source_type='task'`，`source_id=task_id`，`actor='system'`，幂等键 `kind||':'||task_id` |
| 发放族 `grant` | `task_id IS NULL`，`source_type IN ('signup','manual')`，`actor IN ('system','admin')`，幂等键 `'grant:'||source_type||':'||source_id` |

唯一索引 `(task_id, kind)` 保留：PostgreSQL 的唯一索引不约束 NULL，因此多条发放事件可以共存而不影响任务事件"每任务每类至多一条"的语义。

#### `credit_grant` 的裁决点

`credit_grant(p_user_id uuid, p_credit_tenths numeric, p_source_type text, p_source_id uuid) RETURNS uuid`，`SECURITY DEFINER`、owner 所有、仅 owner 有 `EXECUTE`：

1. **金额**：`1 ≤ p_credit_tenths ≤ bigint 上限` 且必须是整数，否则 `22023 CREDIT_GRANT_INVALID`；`signup`/`manual` 之外一律拒绝。
2. **actor 由数据库派生**：`signup → 'system'`，`manual → 'admin'`，调用方不能声明 actor。
3. **幂等**：`pg_advisory_xact_lock('credit_grant:'||幂等键, 631)` 串行；同键已存在且用户/金额一致即重放返回原事件，不一致报 `23505 CREDIT_GRANT_CONFLICT`。
4. **发放即开户**：`INSERT INTO credit_accounts(user_id) VALUES (...) ON CONFLICT DO NOTHING`，随后 `UPDATE ... SET available_tenths = available_tenths + p WHERE user_id = $1 AND available_tenths <= 9223372036854775807 - p RETURNING *`；不满足条件即 `22003 CREDIT_BALANCE_OVERFLOW`。
5. **用户是否存在交给外键**：owner 不持有 `users` 的任何读权限，因此不做 `SELECT FROM users`；`credit_accounts_user_id_users_id_fk` 的 `23503` 由 CLI 映射为 `CREDIT_USER_NOT_FOUND`。

#### 触发器调整（唯一一处偏离"新建函数"惯例）

0024 的 `credit_ledger_events_task_owner` 触发器对所有行校验"事件用户 = 任务属主"，发放事件没有任务，`PERFORM 1 FROM generation_tasks WHERE id = NULL` 必然命中 `CREDIT_TASK_OWNER_MISMATCH`。

直接 `CREATE OR REPLACE` 原函数**不可行**：迁移身份以 `GRANT ... WITH INHERIT FALSE, SET TRUE` 加入 owner，`has_privs_of_role` 为假，既不能替换 owner 所有的函数，也不能 `ALTER FUNCTION ... OWNER TO` 或 `GRANT EXECUTE`。因此 0029 新建同义函数 `credit_check_ledger_task_owner()`（归迁移身份所有，可直接挂触发器），把账本触发器改成它并加 `WHEN (NEW.task_id IS NOT NULL)`，最后在 ownership 块里把函数属主交给 owner。`credit_reservations` 上的同名触发器不做改动。

| `balance` | `--user-id <uuid>` | 只读；账户不存在返回 `exists:false`，不伪造 0 |

环境：`LEDGER_DATABASE_URL`（优先，或沿用 `PUBLISH_DATABASE_URL`）作为管理员身份，`DATABASE_URL` 做目标确认；复用价格发布已验证的 `createOwnerSessionPool` / `withOwnerTransaction`：事务外语句拒绝、`BEGIN` 后 `SET LOCAL ROLE` 到 owner 并回读 `current_user`、事务结束自动失效、全程不 `GRANT` 任何角色。金额上限按 bigint 在连库前拒绝。

#### 4.3.25 HTTP 收费入口：0030 双函数与免费档零冻结（历史实现记录；验收现状由 §4.3.26 取代）

#### 缺口

0024–0029 把「冻结 → 结算 → 释放」和「发放」都做完了，但账务链在 HTTP 层仍是断的：`/api/tasks` 只有两个提交实现——默认的 `createTasksHandler`（免费建任务，`routeResolver` 可选、无报价）与本地 mock 的 `createRoutedTaskHandler`（强制可信路由快照，但仍不收费）。运行身份（`pt_runtime_*`）对 `pricing_versions` / `pricing_quotes` / `credit_ledger_events` 一律 `42501`，`credit_charge_task` 这类函数也还不存在。也就是说**没有任何入口能把「报价」变成用户实际被扣的钱**。

#### 0030：两个 owner 专属函数

| 函数 | 用途 | 关键点 |
|---|---|---|
| `pricing_versions_for_submission(p_logical_model_pk uuid)` | 只读价格时间轴 | `STABLE SECURITY DEFINER`，`search_path = pg_catalog, pg_temp`；只返回报价所需列，运行身份不能借此改价或看历史配置正文 |
| `credit_charge_task(p_owner_id, p_task_id, p_pricing_version_id, p_snapshot, p_snapshot_hash, p_credit_tenths, p_created_at_us, p_expires_at_us)` | 落不可变报价 + 冻结 | 幂等（同任务已有报价即重放返回原行 + `replayed=true`）、`pg_advisory_xact_lock(hashtextextended('credit_charge:'||p_task_id, 629))` 串行、金额/哈希与 `snapshot->>'credit_tenths'` 三方一致才继续 |

`credit_charge_task` 的裁决顺序：

1. 任务必须存在且属于 `p_owner_id`，否则 `23503 CREDIT_TASK_NOT_FOUND`；
2. 同任务已有报价 → 直接返回既有 `(quote_id, credit_tenths, event_id, replayed=true)`，**不按当前价重算**；
3. 参数完整性、金额非负整数、64 位哈希、`p_credit_tenths = (p_snapshot->>'credit_tenths')::numeric` 全部不满足即 `22023 CREDIT_CHARGE_INVALID`；
4. 价格版本必须与任务的 `logical_model_pk` 相同，否则 `23514 CREDIT_QUOTE_MODEL_MISMATCH`；
5. `INSERT INTO pricing_quotes(...) RETURNING id`；
6. **`IF p_credit_tenths > 0 THEN event_id := credit_reserve_task(...)`** —— 免费档（`credit_tenths = 0`）只落报价，不建账户、不冻结、不写账本。零冻结判断放在数据库里而不是 JS 分叉，避免两条路径对「什么才算已收费」产生分歧。

#### 权限：迁移只移属主，授权由能切换 owner 的管理员在迁移之后追加

这是本步唯一踩了三次的硬墙：迁移身份以 `GRANT <owner> TO <migrator> WITH INHERIT FALSE, SET TRUE` 加入 owner，`has_privs_of_role` 为假，**既不能 `CREATE OR REPLACE` / `ALTER FUNCTION ... OWNER TO` / `GRANT EXECUTE` owner 所有的函数**；而 `ALTER FUNCTION ... OWNER TO` 还会**清空旧属主在 ACL 上的条目**，并要求新属主对 schema 有 `CREATE`。

最终分工：

- 0030 里只做「建函数（归迁移身份）→ `REVOKE ALL ... FROM PUBLIC` → 临时 `GRANT USAGE, CREATE ON SCHEMA public` 给 owner → 两个 `ALTER FUNCTION ... OWNER TO` → `REVOKE CREATE`」。迁移文件**不假设运行角色存在**，也不做任何转授权。
- 运行角色的 `EXECUTE` 由 `lib/server/db/runtimePermissions.js` 新增的 `grantChargedSubmissionPermissions(client, role, ownerRole)` 在**迁移之后**完成：先 `GRANT INSERT(logical_model_pk, route_snapshot, route_snapshot_version, route_snapshot_hash) ON generation_tasks`（任务行仍由 Web 自己插），再 `BEGIN → SET LOCAL ROLE "owner" → 回读 current_user 校验 → GRANT EXECUTE 两个函数 → COMMIT`。
- 调用点只有两处：`scripts/local-registration.js`（`PAINTTRACK_CHARGED_SUBMISSION=1` 时用管理员连接追加）与验收夹具（用完 `REVOKE` 复原）。默认 `grantWebRuntimePermissions` **一个 `credit_`/`EXECUTE` 都不含**。

运行身份拿到的仍然只是「读价格时间轴 + 报价冻结」两个函数入口，对定价表与账本零直接读写。

#### `lib/server/tasks/chargedSubmission.js`

`createChargedSubmissionService({ pool, routeResolver })`，`routeResolver` 是构造期硬依赖（不接受调用方临时塞路由/快照）：

1. **事务外**：校验 `ownerId` UUID 与幂等键 `^[A-Za-z0-9._:-]{8,128}$`，`validateCreateTaskRequest` + `requestFingerprint`，再 `assertTrustedRoute(await routeResolver.resolve(...))`——路由解析失败不占事务、不留账务写入；
2. **事务内**（`READ COMMITTED`）：`pg_advisory_xact_lock(user:key, 625)` → 查既有任务 → 有则比对指纹（不同即 `IDEMPOTENCY_KEY_REUSED`）→ `replayCharge`（`credit_charge_task($1,$2)`，遇 `CREDIT_CHARGE_INVALID` 转 `TASK_REPLAY_UNCHARGED`，**拒绝给旧免费任务补收费**）；
3. 无既有任务：`lockModel`（advisory 626 + 读 `logical_models`）→ 校验 `enabled` / `supported_operations` → 校验路由指向同一模型与同一 `catalog_version` → `pricing_versions_for_submission` → `clock_timestamp()` → `createTrustedQuoteService(...).quote(...)` → `config_hash` 与选中版本一致 → `INSERT generation_tasks`（含路由四列）→ `credit_charge_task(...)` 全八参。

HTTP 语义映射（不透传 SQL 细节）：`CREDIT_INSUFFICIENT` / `CREDIT_ACCOUNT_NOT_FOUND` → **402**；`CREDIT_QUOTE_EXPIRED` / `CREDIT_QUOTE_TASK_MISMATCH` / `CREDIT_TASK_NOT_FOUND` / `CREDIT_QUOTE_MODEL_MISMATCH` / `CREDIT_CHARGE_INVALID` / `IDEMPOTENCY_KEY_REUSED` / `NO_ACTIVE_VERSION` / `MODEL_ROUTE_*` → **409**；`CONFIG_INVALID` / `PRICING_SNAPSHOT_MISMATCH` / 未知数据库错误 → **503**；`INPUT_INVALID` → **400**。

## 5. 管理员与运营侧

账户中心不等同于管理后台。后续管理员财务/运营页面应与用户侧分离并走阶段 8：

- 按用户 ID/邮箱查找账户（受限查询和审计）

## 6. API 草案

以下仅定义边界，实施时须按现有 HTTP/会话模式细化错误码、分页、权限和审计：

- `GET /api/auth/me`：增加最小身份字段；只读、no-store；无效/过期会话返回 `user: null`。
- `GET /api/account/summary`：身份概览、账务模块状态和（未来）服务端权威可用/冻结额度；owner 由会话解析。
- `GET /api/account/ledger?cursor=...&limit=...`：用户账单事件 keyset 分页，不接收 owner ID。
- `GET /api/account/usage?cursor=...&limit=...&filters=...`：用户可见任务用量，账务接通前可仅列任务并将扣点状态标为未启用。
- 后续内部服务：任务提交与额度预留必须在同一事务/可靠幂等流程协调；退款、充值、调整写账本事件，不能开放任意客户端写入口。

API 若阶段一只支持身份信息，则不应为了空页面提前伪造完整账单 API；页面可用显式 `featureStatus`/静态路由状态，但未来真实字段必须由服务端返回。

## 7. 安全、隐私与可访问性验收

- 所有账户 API 从会话推导 owner；跨用户读取返回统一无权限/不存在语义，不能泄漏账户是否存在。
- 邮箱按必要性展示；用户 ID 可复制但不作为授权凭证。身份 API 设置 `Cache-Control: no-store`，响应不含 token、密码哈希、Provider 凭据或内部成本细节。
- 账务写入使用数据库事务、唯一幂等键、CHECK 约束和权限分层；Web 角色无权直接改余额投影或账本历史。
- 账户页面正确区分加载、空、未启用、网络失败和服务不可用；键盘可达、焦点可见、屏幕阅读器标签明确；余额数字始终附单位及“可用/冻结”语义。
- 账户导出/删除必须先定义保留期限、法定/运营留存、任务与对象删除、账务凭证保留及恢复期；不能用简单删除 users 行替代完整流程。

#### F. 审计、性能与停止条件

- 每请求记录 `admin.models.read` accepted/rejected 的 requestId、已认证 actorId、固定 outcome；系统日志仅固定 service/event/errorCode/durationMs/requestId，不记录 q/完整 URL/cursor、邮箱、token、SQL、config、endpoint、原异常或完整 DTO。`lib/server/observability.js:2–9,40–62` 的 writeLog 不含 actorId 白名单，actorId 应走 emitAuditEvent，不能误以为传入 writeLog 就已审计。现有 emitAuditEvent 是结构化 sink 日志，**不是持久审计库**；本轮不写 provider_config_audit_events（动作枚举也无 read）。真实启用前独立确认 sink 留存/访问/失败策略；未批准策略或必要审计不可用则停止，不声称已有持久审计。只读不引入写操作 step-up，但不降低 admin+MFA。
- 请求预算候选：20/最多50模型；每模型最多50绑定，DB端有界 limit+1 检测超限，返回整体503而非默默截断；单响应 UTF-8 JSON 上限256KiB，超限503。最多一次分页查询＋一次按本页PK集合的批量绑定查询，无 N+1、无所有历史/完整配置加载。绑定函数也须强制 PK数量及每模型结果上限，不能仅信任 HTTP limit。READ ONLY 不是唯一防线，函数审查还要证明没有副作用/外部调用。
- 使用事务内 SET LOCAL statement_timeout=5s、lock_timeout=1s（待真实带量验收，不是性能已通过），不取行锁/账务 advisory lock；正常/异常/中止后 rollback/commit、释放连接并验证池只读/超时/身份复原。使用模型业务ID唯一索引和绑定 logical_model_pk/priority 索引；名称 contains 搜索未必命中现有索引，不能靠limit声明低成本。未来代表性隔离数据 EXPLAIN (ANALYZE,BUFFERS) 量化计划/扫描/扇出/排序/响应字节，达不到预算停止另审，不自动加索引或迁移。
- **硬停止条件：**Web 现有权限不足即停止；任何内部Provider/绑定/价格基表 SELECT、owner/Worker借权、收费授权挪用、未经另行批准的新GRANT/迁移、secret/config/endpoint/token/owner进入投影、未知JSON假档位、价格无权却标未配置、当前目录改写历史、混源/fallback、无有效admin+MFA/审计门禁、ACL/性能/池复原失败，都不得继续真实API接线/启用。不连接现有业务库试错，不索要真实凭据以完成本轮设计。

### 产品边界

1. 用户侧 `/account` 与 `/zh/account` 只展示当前登录用户自己的身份、余额和账单流水；不得在其中塞入用户列表、封禁、解封、额度调整或其他管理操作。
2. 管理员使用独立的后台页面与导航入口（建议 `/admin`、`/zh/admin`），后台服务端每个管理 API 都必须再次校验当前会话的 `role=admin`，不能依赖前端隐藏按钮。
3. 管理员登录仍复用现有认证体系；进入后台和执行敏感操作分别要求管理员 MFA/step-up。不得创建第二套密码、第二套管理员会话或把 bootstrap CLI 变成网页升权入口。
4. 当前单人运营不引入多级审批、替补管理员、复杂工单或多人 SLA；但保留最小权限、幂等、事务回滚、审计、最后一个管理员保护和未知状态不自动处置等安全边界。

### 历史实施顺序与依赖（已被 2026-11-19 新顺序取代）

以下保留旧路线用于追溯，不再要求用户只读之后立即做账号处置；相关安全约束继续有效，持久审计必须先于对应敏感操作：

1. **后台壳与认证门禁**：独立路由、管理员入口、服务端 admin/MFA/step-up 门禁、未授权返回和基础审计；先只读，不开放写操作。
2. **用户管理只读**：用户列表、精确邮箱搜索、分页、用户详情、账号状态、邮箱验证、活跃会话、余额/冻结额度/最近账单摘要；不显示密码、token、MFA secret 或完整 IP。
3. **账号处置**：新增 `active/suspended/deleted` 状态模型及状态事件；实现临时/永久封禁、解封、撤销全部会话。封禁不删除资产、不清零余额、不释放冻结、不伪造任务终态；每次操作要求原因并写结构化审计。
4. **高风险操作保护**：封禁/解封/全会话撤销/角色和额度变更等操作要求 MFA/step-up、影响预览、幂等键、重复提交保护和失败整体回滚；保护管理员自封禁与最后管理员移除。
5. **风险事件只读**：登录失败、密码/MFA恢复、异常任务/额度、管理员敏感操作等事件进入 `security_risk_events`；先做可解释的 low/medium/high 三档与人工确认，不先做不可解释的风险分数。
6. **审计查询与后续运营写操作**：`admin_audit_events` 追加写入、按用户/动作/时间过滤；人工额度发放、退款、价格/Provider 配置等分别依赖对应账务、支付、Provider 门禁，不能因为后台壳完成就一并开放。
