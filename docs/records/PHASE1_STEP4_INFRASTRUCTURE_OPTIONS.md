## 2. 现状与约束

### 2.1 已确认的产品/架构约束

- Web SaaS 是主要产品，Electron 是辅助客户端；浏览器与 Electron 云端模式只访问 PaintTrack API。
- PostgreSQL 是事务权威；额度冻结/结算/释放、幂等、任务状态和对象归属必须由服务端维护。
- 任务必须持久化，独立 Worker 执行，并支持租约、超时、有限重试和故障恢复。
- 对象默认私有，供应商 URL 只能作为临时地址；内部 `asset_id` 与所有权元数据由 PaintTrack 管理。
- 首期邮箱登录；密钥只放服务端；Electron 本地推理不进入云端额度路径。
- 继续使用 JavaScript，React 与 Next.js 锁定版本依照外部开发规范，不在此步骤调整。

### 2.2 仓库核查范围内的事实

- 根 `package.json` 声明 Next `^15.0.0`、React/React DOM `19.2.4`、Electron `^33.4.11`、Vite `^5.4.0`；锁文件解析到 Next `15.5.28`、React/React DOM `19.2.4`、Electron `33.4.11`、Vite `5.4.21`。这些依赖在 [package.json](./package.json) 与 `package-lock.json` 中核对。
- Web 入口使用 Next App Router；根脚本包含 `dev`、`build`、`start`、`lint`、`test`。Electron 则通过 Vite 构建静态前端并由 Electron 主进程加载。后端服务代码若引用 Node-only 数据库驱动，必须限制在 Next Node runtime/API 服务端及 Worker，不得进入浏览器 bundle 或 Electron renderer。
- Dockerfile 使用 Node 22 Alpine 构建并运行 Next；当前 `docker-compose.yml` 仅定义单体 `painttrack` Web 服务，没有数据库、Worker、对象存储或邮件服务定义。
- 在主清单、锁文件依赖项和主应用源码/schema 的本次审查范围内，未发现 PostgreSQL 驱动、ORM、数据库迁移、持久 Worker、事务邮件或自有资产库实现证据。此为审查范围内观察，不代表外部服务中绝对不存在。
- 现有上传路径主要对接 MuAPI/S3 预签名上传；浏览器 `localStorage` 中的上传历史不能满足服务端资产目录、长期所有权和授权要求。

本报告只评估，不创建 schema、迁移、认证、队列、bucket 或云服务。用户已确认技术方向、首期中国大陆市场、低预算低维护起步、预算后续可逐步到 ¥100–300/月及 Worker 单次任务几秒至几分钟；云服务商、地域、账户、域名、预计负载/流量、数据驻留、恢复目标及预算取舍现作为后置评估项，不阻断本地阶段 2 开发。阶段 2 仍须按小步骤逐项实施、测试和验收；真实外部服务、预发布或生产部署前须完成专项评估并取得用户确认。

## 3. PostgreSQL 访问层与迁移工具

### 3.1 候选比较

| 方案 | 优点 | 代价/风险 | 与 PaintTrack 的适配判断 |
|---|---|---|---|
| Drizzle ORM + drizzle-kit | TypeScript/JavaScript 友好；schema 与 SQL 关系直观；生成 SQL migration 易审查；便于使用 PostgreSQL 事务、约束、索引和行锁；可仅在服务端 Node runtime 与 Worker 使用 | 生态与团队经验可能不如 Prisma 普及；复杂报表或特殊锁语句仍需理解 SQL；生成迁移需要严格审查，不能直接假定自动迁移安全 | **推荐**。PaintTrack 需要高可审查的账务事务、幂等约束和任务领取，SQL 可见性优先于隐藏抽象；符合当前 JavaScript 技术栈。须在实现步骤确认具体驱动与连接池方式 |
| Prisma ORM + Prisma Migrate | 开发者生态成熟；schema 与生成客户端体验清晰；迁移工作流完善；关系查询较易上手 | 生成步骤和 schema 抽象增加构建/部署约束；账务锁、`SKIP LOCKED` 与复杂事务仍需原生 SQL；连接池/Serverless 与运行环境需要额外核实；对当前 Node 容器可行但须验证打包路径 | 可接受备选。若团队已有 Prisma 经验，熟悉度可抵消生成与原生 SQL 混用成本 |
| node-postgres (`pg`) + 手写 SQL/migrations | 控制最直接、抽象最少，交易语义和 SQL 完全显式；依赖面小 | 需要自行建立参数化查询封装、schema 类型映射、迁移版本与执行纪律；长期维护负担和人为不一致风险较高 | 不建议作为默认，除非团队有成熟 SQL migration 框架/规范；可作为底层驱动而非独自承担全部 schema 管理 |

### 3.2 建议决策

建议采用 **Drizzle + drizzle-kit + PostgreSQL**，migration 文件以审查过的 SQL 为准；应用启动时不自动执行 schema migration。部署时通过独立的一次性 release job 执行迁移，应用与 Worker 在迁移成功后更新。生产迁移采用扩展-迁移-收缩；破坏性变更要求兼容窗口、备份/恢复方案和明确批准。

驱动/连接方式应在实现步骤前做小型兼容性验证：Next Route Handler 明确使用 Node runtime；Worker 为独立 Node 进程；应用请求路径使用受控连接池；测试优先使用真实 PostgreSQL 隔离实例，而不是 SQLite 替代，以覆盖 PostgreSQL 的事务、约束、锁和 JSON 行为。是否用 `pg` 或 `postgres` 作为底层驱动需在实现时依据部署连接池与 serverless/容器拓扑确认，不在本步骤增加依赖。

### 3.3 必要控制

- 额度账本、余额冻结和任务创建在同一事务内；以唯一约束、事务锁/等价并发控制保证幂等。
- Worker 领取与状态改变采用明确的事务边界、租约、心跳、attempt 记录与可恢复状态机。
- Migration 在 CI/隔离数据库验证可从空库重放；提供备份与恢复方案，避免“回滚脚本必然安全”的假设。
- 应用角色与迁移角色分离；应用连接不得拥有任意 DDL 权限。

## 4. 持久任务队列与 Worker

### 4.1 候选比较

| 方案 | 优点 | 代价/风险 | 判断 |
|---|---|---|---|
| PostgreSQL 任务表 + 独立 Worker 轮询/领取 | 不增加 Redis 运维面；任务状态、额度、资产和任务事实在同一数据库；事务内创建任务并冻结额度；可用租约恢复与 `SKIP LOCKED` 实现并行领取 | 数据库同时承受业务读写和队列轮询；需谨慎设计索引、退避、租约、并发上限、死信/人工处置；不可长时间持有事务 | **首期推荐**。负载尚无测量数据，先减少组件与一致性边界；保留清晰接口以便未来迁移 |
| PostgreSQL + Redis/BullMQ | 延迟任务、重试、并发控制、速率限制和调度能力较丰富；适用于明显的队列吞吐/调度需求 | 新增 Redis 的高可用、持久化、告警、备份与成本；数据库任务事实与队列消息双写带来一致性问题，需 transactional outbox 或等价方案；许可证和托管细节须按部署产品核实 | 作为规模/功能增长后的升级选项；当前缺少采用它的实测依据 |
| 进程内队列/内存任务 | 实现简单 | 进程重启、扩容、部署和浏览器断线会丢任务；不支持目标要求的持久状态与恢复 | 不符合基准，排除 |

### 4.2 建议决策

首期以 PostgreSQL `tasks`（及必要的 outbox/attempt 记录）为持久队列，独立 Node Worker 以短事务领取并设置租约/心跳；任务执行、供应商网络调用不得占用数据库事务。采用有界并发、退避、单次自动重试上限、可观测的卡住任务与人工处置机制。任务创建和额度冻结原子提交，Worker 只消费已提交任务，重复领取必须安全。

只有在实际指标显示数据库轮询/任务吞吐、延迟调度、复杂优先级或多队列隔离成为瓶颈后，再引入 Redis/BullMQ，并通过 transactional outbox 保证数据库任务事实与消息投递一致。首期不把 Redis 当作任务事实权威。

## 5. 私有对象存储

### 5.1 方案边界

- 保持 S3 兼容接口是合理的供应商抽象；API 负责所有权、授权、对象键和短时签名，不允许客户端决定 bucket/key。
- 对象与元数据分离：对象存储承载媒体字节；PostgreSQL 保存内部 `asset_id`、owner、对象键、大小、媒体类型、校验状态、生命周期与任务关联。
- 浏览器/Electron 云端上传可优先走受约束的短时直传，避免 Next API 中转大文件；上传完成后必须由服务端验证对象存在、大小、类型/魔数等并标记可用。供应商结果 URL 抓取必须限制固定目标、重定向、DNS、超时和响应大小，禁止通用 URL 代理。
- bucket 默认私有；下载仅经所有权校验后签发短时链接。保留生命周期、删除/导出、备份/恢复和成本限额策略。

### 5.2 供应商选择

本次不建议直接批准某个具体厂商。首期目标市场已确认为中国大陆，但服务部署地域、素材数据驻留要求、已有云账户、对象大小与预计流量、出网/请求成本容忍度、生命周期/版本控制及灾备要求仍待确认。腾讯云 COS 官方价格说明可作为大陆候选的初筛参考：公开价目示例中标准存储约 ¥0.118/GB/月、外网下行流量约 ¥0.5/GB、标准存储读写请求约 ¥0.01/万次；地域、存储类型、请求类型、流量计费和活动价格可能改变最终费用，且下行流量可能高于存储本身成本。以上仅为网页价目参考，不是账户购买报价或价格承诺。购买前需在目标地域控制台核对存储、请求、流量、低频/归档取回、版本与生命周期、备份/复制及税费等项目。之后以 S3 API 兼容、区域/合规、私有访问、生命周期、CORS/签名能力、可观测性、恢复能力和总成本进行同口径比较。

## 6. 邮件服务

### 6.1 要求

邮箱登录至少涉及验证、登录/一次性链接或密码重置通知；需要限速、短时一次性 token（数据库只存 token hash）、错误响应防账户枚举、投递失败处理和审计。邮件服务只负责发送，不作为用户、会话或授权的权威数据源。

### 6.2 建议

在服务端定义窄接口（如 `sendVerification`、`sendLoginLink`、`sendPasswordReset`），由 adapter 适配事务邮件供应商。发信域名需 SPF、DKIM、DMARC；对退信、投诉和抑制列表建立处理，限制测试/生产收件域。供应商凭据仅进入部署密钥管理，不写入仓库、客户端或日志。

具体服务商当前不选定：须结合中国大陆用户的实际投递质量、数据处理/驻留要求、发信域名控制权、API/Webhook 可用性、月发信量、退信事件、成本和支持能力评估。腾讯云邮件推送官方价格说明提供按量约 ¥0.0019/封、每账号 1000 封免费额度的公开参考；独立 IP 约 ¥900/月，明显不适合当前起步预算。账户资格、免费额度适用范围、实际投递能力、欠费停服条件和当前价格均须在开通前核验；不把公开价目视为已获得服务资格或送达承诺。邮件供应商选择仍需验证域名认证、限额、退信/投诉事件与支持能力。

## 7. 部署环境与运行拓扑

### 7.1 建议拓扑

```text
Internet
  -> HTTPS ingress / reverse proxy
      -> PaintTrack Web/API container (Next.js, Node 22)
          -> managed PostgreSQL (private network, TLS, backups)
          -> private S3-compatible object storage (short-lived signed grants)
          -> transactional email provider (server-side adapter)
      -> PaintTrack Worker container (separate process, bounded concurrency)
          -> PostgreSQL task leases + provider adapters
          -> private object storage
          -> MuAPI (server-side credentials)

Release job (one-shot): validated PostgreSQL migrations before app/worker rollout
```

### 7.2 平台模式比较

| 模式 | 优点 | 代价/风险 | 判断 |
|---|---|---|---|
| 大陆轻量应用服务器 + 托管 PostgreSQL + 独立 Worker 进程 | 月费直观；同机可先运行 Web/API 与独立 Worker，保留容器/进程边界；托管 DB 降低数据库补丁与备份运维 | Web/API 与 Worker 共用主机资源，主机是单点；主机补丁、监控、进程恢复仍需管理；扩缩需迁移或拆分服务；数据库费用可能超过当前预算 | **维护负担较低，但当前报价明显超出低预算起步目标**；仅在接受较高月费且核实网络互通后考虑 |
| 单台轻量服务器自管 PostgreSQL，Web/API 与 Worker 分进程 | 复用用户已有的低价服务器候选，省去独立托管数据库月费；服务边界仍可按独立进程/容器组织 | 主机与数据库共用资源且都是单点；团队负责数据库补丁、访问控制、备份、异地副本、恢复演练、监控与故障响应；主机故障可能同时中断应用并影响本机备份 | **最低现金支出候选，适合验证期而非默认生产基线**；仅在用户明确接受自运维责任、并先定义备份/恢复方案后评估 |
| 单台 VPS 自管容器、数据库和队列 | 单机账单可能较低且控制权高 | 数据库备份/恢复/升级、网络隔离、密钥、监控与安全补丁均由团队承担；不符合当前先少维护跑通的优先级，也有单点故障；当前 Compose 仅有 Web，不等于生产就绪 | 作为后续逐步自运维/迁移选项，需先具备恢复演练与安全维护能力 |
| Serverless 函数 + serverless PostgreSQL | Web 请求按需扩展、较少管理常驻实例 | 长耗时 Worker/供应商轮询、运行时限制、数据库连接池/冷启动和出站网络需特别验证；当前 Docker/Worker 目标模型不天然等价 | 当前不作为默认；需明确 serverless 平台和执行时限后专项评估 |

**初筛结论：**“轻量主机 + 托管 PostgreSQL”可降低数据库维护负担，但按现有公开参考与用户报价，预计基础规格已经约 ¥207.17–¥212.25/月（¥38 若为首年总价、¥99/年续费成立；若 ¥38 是月价则约 ¥242/月），不含数据库存储/备份、对象存储下载流量、域名/备案及可能的网络互通费用；因此与当前低预算快速跑通的目标不匹配，不能再笼统说成“服务器本身两百多元/月”。其中轻量服务器本身按用户提供的 ¥99/年续费报价折合约 ¥8.25/月，超过 ¥200/月的主要部分是托管 PostgreSQL 的公开参考价约 ¥204/月。以上报价均须在购买页核实，不是当前账户最终报价。

**低现金支出备选：**把 PostgreSQL 与 Web/API、独立 Node Worker 一起部署在同一台轻量服务器。按用户提供的续费报价，服务器部分约 ¥8.25/月；数据库软件本身不另收云数据库实例费，但总账单仍会包括服务器磁盘/流量超额、对象存储和下载、邮件、域名/备案等，需按实际使用核算，不能据此承诺完整生产成本。该选项改变了用户已确认的“托管 PostgreSQL”基线，故这里只列为待决策候选，不视为已批准架构变更。代价是团队必须自行承担数据库安全补丁、最小权限、备份与异地副本、恢复演练、监控和故障响应；应用、Worker、数据库共处单机，主机故障会同时影响服务与数据库可用性。若用于验证期，应至少确保数据库不开放公网、自动备份离机保存、定期执行恢复验证，并限制实例并发与磁盘占用；做不到这些控制时，不应为省月费而采用。

轻量数据库、低价活动套餐及标准 CVM + 托管 PostgreSQL 也可作为后续询价方向，但当前没有取得足以确认账号可购性、地域、规格、网络费和续费条件的一手报价，因此本报告不填入未经核实的具体价格。轻量服务器与托管数据库之间还需核实网络互通方式及相关费用；不能默认内网可直连。建议按“购买页截图/规格单 + 目标地域 + 首年应付 + 续费价 + 存储备份 + 网络与流量”的同口径核算后再比较。

轻量主机上可用独立容器/进程运行 Node Worker，但同机只是进程隔离，不是高可用；主机故障会同时影响 Web 与 Worker。

### 7.4 部署控制要求

- Web/API 与 Worker 分开进程/服务；共享同一应用代码和版本，但各自最小权限、健康检查、并发限制和独立扩缩。
- PostgreSQL 不对公网开放；TLS、自动备份、明确保留周期和恢复演练；生产应用角色与迁移角色分开。
- 所有密钥通过部署平台密钥管理/运行时注入；开发、测试、预发布、生产隔离。
- 迁移 job 可重复审查且单次执行；先迁移再滚动更新，失败时停止发布并按恢复预案处理。
- 日志不得记录完整 prompt、token、供应商 key、私有对象 URL 或不必要的媒体/个人数据；建立任务积压、失败率、Worker 心跳、DB 连接、存储量和供应商成本告警。
- 现有 Compose 可作为开发/集成环境扩展起点，但须另设独立 Worker、PostgreSQL 与隔离的测试存储配置；不把本地 Compose 直接等同生产部署。

## 8. 建议 ADR

### ADR-006：数据库访问层与迁移

- **建议状态：**用户已确认技术基线；具体供应商与运行参数待定
- **建议决策：**Drizzle + drizzle-kit，审查并提交 SQL migrations；生产使用独立 release job 执行；迁移前置备份/恢复策略。
- **原因：**JavaScript 兼容，SQL/约束/事务可见，适合额度账务与 Worker 领取场景。
- **备选：**Prisma + Prisma Migrate；若团队熟悉度优先，可作为替代，但仍需为关键账务/锁语义审核原生 SQL。

### ADR-007：首期队列实现

- **建议状态：**用户已确认技术基线；具体供应商与运行参数待定
- **建议决策：**PostgreSQL 持久任务表 + 独立 Node Worker；首期不引入 Redis/BullMQ。
- **原因：**任务、额度和所有权可在单数据库事务里建立事实；无当前吞吐数据支撑额外队列服务。
- **升级条件：**指标证明调度复杂度、吞吐、延迟或隔离需求超出数据库队列能力；届时通过 outbox 保证双系统一致。

### ADR-008：对象存储接口

- **建议状态：**S3 兼容私有存储接口已符合基准；具体供应商待确认
- **建议决策：**服务端签名、私有 bucket、内部 asset_id、上传完成确认、短时授权下载。
- **未决：**供应商、区域、数据驻留、生命周期、恢复与成本。

### ADR-009：邮件与部署

- **建议状态：**用户已确认技术基线；具体供应商与运行参数待定
- **建议决策：**邮件 adapter + 事务邮件服务；Web/API、Worker 分离容器，托管 PostgreSQL，对象存储独立，迁移单独 release job。
- **未决：**供应商/平台、部署区域、首期可接受支出及 ¥100–300/月范围的软/硬上限、域名、已有账户、运维职责、备份恢复目标。
